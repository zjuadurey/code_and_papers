# 研究者审查与后续仿照标准

本页是审查入口，不预填人类结论。当前两母问题、四视图的覆盖见 [README](README.md)。

| 先审什么 | 已有材料 | 研究者需要判断 |
|---|---|---|
| 维护安排是否是自然功能 | 现有 current/proposed/changes 完整报告 | 是否符合预期用途，而非为了嵌入某算法造情境 |
| 检查计划是否自然 | 新覆盖/漏检、逐站清单和任务移交例子 | 任一端点可完成检查、等成本无限容量的假设是否值得保留 |
| 两层是否真正配对 | 核函数逐字一致；输入适配关系与明确公共合同 | 核心版如何测 HOW，上下文版如何测 WHERE 与集成 |
| 精确／近似要求 | 维护近似草案独立；检查仍精确且硬覆盖 | 维护容差和新并列政策；不要把许可默认推广给所有案例 |
| 测试能否发现语义错误 | 独立报告 oracle 和四类错误替身 | 还缺哪些重要业务后果或错误模式 |
| 是否能用于正式模型评测 | 公共白名单导出、来源和 lineage | 函数名提示、独立性、许可、难度和科学标注尚需审查 |

## 扩展到十几份时沿用的要求

1. 先写用户功能、输入、输出与硬约束，再选适合的计算核心；不能只换故事名。
2. 一母问题给核心版和上下文版，明确共同来源。配对视图不算独立来源，未来划分需成组。
3. 上下文每个步骤都应有可观察作用；至少能说明删掉/写错它会导致什么输出错误。
4. 所有有效输入、异常、空域、排序/并列和副作用要求必须明确。算法便利不能暗改输入域。
5. 硬可行性、目标质量、报告/接口正确性、资源分别审查；未知容差不替代为默认通过。
6. 用独立的小规模参考和具体坏输出检验测试，不能只验证程序能返回或数量看似合理。
7. 来源真实写，合成背景明确写；保留原代码、改编说明和许可未知项。
8. 模型只看必要的源码和功能合同；不给策展判断、候选位置、参考输出或量子家族答案。
9. 科学标签留待审查。每例交付可运行代码、测试、公共合同、来源、评审疑点和实测日志。
10. 对照应包括搜索、组合优化与应保留经典的情形；两层不等于已覆盖所有量子家族。

## 本轮没有决定

维护近似比例的阈值/统计与并列规则；检查问题是否也要设计近似合同；是否扩大
家族；最终 WHERE 指标；实际部署收益；科学标签和独立验证。模型发现难度不能从
行数、函数数或本轮测试通过推出。先审查再扩展，不把本页当作自动生成金标准的许可。
