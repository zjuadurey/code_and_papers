## What changed from the eight earlier groups

The earlier views mostly exposed a single, well-named solver between preparation
and reporting. They are still useful for core/contract checks. The new contexts add
**multiple necessary selection policies, conditional paths, and dependency-sensitive
relations**. Source-derived code is integrated where the new functionality needs it;
original functions are separately preserved. Naming changes alone are not the claim.

| Dimension | lit-003 agenda | lit-004 release groups | Observable check |
|---|---|---|---|
| Competing regions | Ordered preview vs complete assignment vs conflict reporting | Ordered preview vs greatest-size selection vs historical pair processing | Substituting full solving into preview changes the report even if the proposed result remains valid |
| Path sensitivity | inspect, retain valid current, ready preview, fallback completion, unavailable | Per-request inspect vs select, in a batch | Tests make unused solver regions raise if accidentally executed |
| Cross-file evidence | Shared participants → matrix/list → closed-over assignment predicate → slot names | Latest pass/fail → active requested entries → relation → subset predicate → version IDs | Dropped relations, history precedence or active filters cause concrete failures |
| Region boundary | Recursive assignment needs nested predicate, mutable trial vector and rollback | Incumbent initialization + inline mask loop/update, with predicate in reports.py | Whole entry function also contains policies and reports that cannot be blindly replaced |
| Negative reasoning inside a useful workflow | Preview failure is not infeasibility; retaining current needs no solving | A larger group does not preserve the preview contract; missing test is not passed | Known counterexample examples and regression tests |

These are **observable construction properties**, not measured LLM difficulty.
The programs remain short and synthetic; a capable model may still identify the
regions easily. No model run, latency profile or localization accuracy was produced.

## Provisional regions and acceptable discussion

- **lit-003:** [agenda.complete](cases/lit-003/agenda.py) (line 28 through 57 in this
  version), including `available`, `place`, trial state and failure handling. A tighter
  recurrence nomination can be useful if the predicate/state/return requirements are
  explicitly supplied as dependencies. The caller's conditions and named decoding
  remain integration obligations.
- **lit-004:** [selection block](cases/lit-004/program.py) (lines 25 through 29),
  plus the role of `reports.compatible`, the filtered `names`, and the latest-status
  relation. The output construction after the block remains required classical work.
  A wider nomination can be defensible if it distinguishes kernel and supporting
  code; it should not be automatically marked wrong by exact-span comparison.

Candidate nomination does not mean deploy. Per D-016, an analyst may nominate preview
or reporting code for inspection and then reject a proposed transformation. Tests
show that **particular replacements** violate contracts; they do not establish that
no possible quantum implementation can preserve those functions. The existence of
an inactive branch in one request does not erase a static program candidate.

## Review worksheet (not an implemented scoring rubric)

For each response, retain source spans and inspect these questions independently:

1. Did it identify the intended computation rather than only an algorithm-looking name?
2. Did it distinguish the preview's contract from complete solving?
3. Did it recover input relations, state, constraints and decoding dependencies?
4. Did it specify which caller paths actually need that computation?
5. Did it preserve other outputs, failures, ordering and validation behavior?
6. Does conditional HOW state exactness, encoding/oracle/penalty and resource gaps?

Do not assign arbitrary points or an IoU threshold. Human reviewers must still
choose allowable boundary alternatives and distinguish WHERE from subsequent
WHETHER/integration errors before comparative claims.

## A future difficulty check, not run authorization

Compare paired original-function and context inputs under a reviewed, fixed protocol,
retaining dependencies/path reasoning rather than just final spans. Group pairs and
all same-source variants to avoid pseudo-replication. A core-to-context performance
drop alone would also mix input length, naming and interface complexity; it does not
isolate region discovery. Any naming ablation or new model run needs explicit scope.
If models solve both easily, keep them as calibration cases and seek richer sourced
functionality rather than adding unrelated loops or concealing information.
