## 实际发生了什么

同一个 `gpt-5.6-sol / medium` 进行了 **4 次实际调用**，按以下顺序输出 JSON 动作，
控制器执行动作并把结果放进下一轮输入。没有人工插入方案、替换电路或修复模型回答。

| 轮次 | 模型选择的动作 | 实际结果 |
|---|---|---|
| 1 | `read_program` | 读取原 `program.py`、`kernel.py`、公开任务与四节点工作负载 |
| 2 | `verify_candidate` | 模型生成 QAOA 电路，4 逻辑比特、20 门、64 shots；QDK 本地模拟通过 |
| 3 | `estimate_cost` | 实际调用 QDK 资源库，测量主机及经典成本，返回完整假设场景和盈亏平衡条件 |
| 4 | `finish` | 模型读取工具反馈，输出 `REMAIN_CLASSICAL` 及资源条件解释 |

返回结果为分离权重 4、维护窗口 `[A,C]` 和 `[B,D]`，与原程序一致。
实际采样成功，**没有使用经典回退**。另外检查 16 种单次测量结果、空结果与异常候选，
21/21 符合原行为；失败样本走原程序。可信证书和回退是 harness 提供的工具，
电路与计划由本次模型生成。工具选择和参数通过 JSON 动作协议传递；不是供应商原生 function call。

输入明确要求该实例的 QAOA 小方案，没有向模型提供旧电路、参考答案、标签或历史响应。
这是单案例集成运行；不等于已经实现从任意程序自动发现量子算法或任意规模代码生成。

## 成本结论

| 假设物理门时间 | QDK 物理比特 | 单 shot 时间 | 64 shots 加主机总成本 |
|---|---:|---:|---:|
| 100 ns | 279 | 36 μs | 2.411–2.431 ms |
| 1000 ns | 279 | 360 μs | 23.147–23.167 ms |

原始枚举程序测得 28.24–32.08 μs；针对二分图的经典着色对照为 7.81–9.46 μs。
本次方案的主机部分约 106.93–127.18 μs，因此该小实例在当前场景下保留经典实现。
这是一个成功运行的量子化方案及成本判断，结果不是正向加速。

条件为 `64 × t_shot + H < T_classical`，并满足该估算点的物理比特需求。
当前 `T_classical - H < 0`，所以增加量子比特不会让这个固定方案获得收益。
279 是两个指定模型点的估算值，**不是搜索所有架构所得的全局最小门槛**。

六项成本账本已填齐：准备、控制、通信、读出解码、验证/回退、编译摊销。
准备/解码/验证与经典运行时间来自本机测量；控制和通信各 1 μs 是显式假设。
固定电路按稳态已离线编译、每次请求编译摊销设 0；未把离线 LLM 开发或冷启动算进热路径。
验证/回退成本取成功证书与始终回退两条路径的描述性测量范围，没有靠理想成功率打折。
区间是本机批次测量范围，不是统计置信界；跨机器会变化。

原共享估算器把物理 shot 错误做 union bound，返回 `quality_not_established`；
本工具独立检查证书/回退后的输出正确性，不改写共享估算器原结果。
模型终稿也保留了这项保守告警；它不意味着证书已接受的答案有 0.398 的出错概率。
硬件是否完成执行、经典主机故障不在这次模型中。没有 QPU 调用。

## 在其他机器上跑

同步整个项目，包括未提交的新文件；环境见[环境文档](../../../docs/quantum_advantage/ENVIRONMENT.md)。
本机使用 `palqo`：Python 3.10.21、QDK 1.32.3、NumPy 1.26.4。
从 `qrefactorbench/` 根目录执行，输出目录必须不存在。

**不调用模型，重放本次模型生成的方案：**

```bash
conda activate palqo
python -B pilot/llm_workflow/lit001-v0.1/replay.py \
  --run pilot/llm_workflow/lit001-v0.1/run-20260928-01 \
  --output /tmp/lit001-replay-new
```

它重新执行量子模拟、行为验证、QDK 估算与本机成本测量，检查保存结果的 hash。
量子模型/参数一致时资源估算应一致；主机时间重新测量，允许跨机器不同。

**重新跑实际 LLM 闭环（会消耗已有模型订阅额度）：**

```bash
conda activate palqo
python -B pilot/llm_workflow/lit001-v0.1/run.py --output /tmp/lit001-llm-new
```

需要 Linux/WSL、`bwrap`、已登录的 Codex CLI（本次 0.157.1）、现有订阅可用的 `gpt-5.6-sol`。
CLI 从 PATH 查找，认证使用当前用户正常登录文件，不在项目中复制凭据。
沿用仓库工具为空的受限推理通道，每轮单次文本推理，无 shell、文件、委派或浏览工具。
控制器最多 8 轮；模型不获得整个仓库。运行前用假认证和断网本地 sink 检查实际请求。
其他 CLI 版本需通过相同预检；模型采样不保证生成相同方案。macOS/Windows 原生可先重放，
完整订阅推理隔离通道目前要求 Linux/WSL。

调用方式参考 [OpenAI 官方非交互文档](https://developers.openai.com/codex/noninteractive)，
具体隔离与调用复用项目既有 transport。未安装新的依赖或创建子 Agent。

## 这次可以学到的最小 workflow

模型负责选动作、写方案、理解反馈；harness 负责执行允许的动作、记录原始结果和控制顺序。
验证器与估算器负责提供可计算的证据。模型不能只说“正确”就跳过验证，也不能在电路改变后
沿用旧电路的成本结论。若工具报错，错误会进入下一轮输入，让模型在预算内修改；
本次首个方案即通过，实际没有发生修订，不把“代码支持修订”说成“已观测到修复”。
