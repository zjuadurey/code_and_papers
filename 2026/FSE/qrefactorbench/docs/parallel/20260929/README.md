# 三窗口并行推进说明

日期：2026-09-29。状态：分工说明及A/B/C独立worktree已建立；研究工作包尚未执行。
研究事实仍以 [PROJECT_STATUS](../../../PROJECT_STATUS.md) 为准，本文件不是另一份总状态。

用户希望开三个窗口并行推进。此前老师讨论明确了三个关注点：以经典/量子实现的同输入输出
和来源参考支撑case；调研加速以外的能力；用有代表性、广泛且有难度的case发现并弥补LLM缺陷。
下面是据此制定的工作组织方案，不将上一轮助手提出的具体方法、扩展家族或指标记为已接受科学决定。
行为保持和端到端收益目标继续成立；自动迁移能力与量子收益分开取证。
后续用户转来的讨论指出，应拆成短期内不依赖彼此新开发结果的任务，并提前设计实验、写background/
evaluation及design草案。据此调整为下列分工，替代最初A案例→B基线→C技术的流水线职责。

## 分工与第一批独立工作

| 窗口 | 负责的问题 | 可立即开始的工作 | 第一批交付 |
|---|---|---|---|
| [A：文献与案例](A_CASES.md) | 任务是否有代表性，参考和研究缺口是否可信？ | 复用现有来源/参考，补覆盖与前沿证据、非时间收益适用性 | 案例/来源/行为参考包、background及related work素材 |
| [B：代码开发](B_IMPLEMENTATION.md) | 已有失败证据支持的技术缺口怎样实现和验证？ | 从固定的旧案例/开发反例出发做最小实现，验证接口与成本记录 | 已测试代码、接口样例、design实现事实 |
| [C：实验设计与论文](C_EVALUATION.md) | 如何检验技术，哪些论文内容可以先写？ | 设计协议/基线/消融/日志字段，写背景、evaluation方法和design草案 | 协议、日志需求、论文diff和待实验清单 |

A/B/C都从同一固定起点独立完成第一批成果，不等待对方尚未开发的产物。
第一轮开始各自在README写明输入版本、输出接口和验收条件；未知接口先给假设/样例，交接时统一核对。
三方交付后才在B做一轮集成：案例/参考＋已测试实现＋实验协议，核对一致性后冻结并运行。
依赖发生在集成节点，不是开发过程中持续等待；每轮只做最小完整交付，不等待全部调研结束。

## 写入范围与三窗口协作

用户可以在原FSE目录启动所有对话；Agent在每次工具调用中指定各自worktree的执行目录，
并使用对应目录下的绝对路径编辑。对话入口共享，实际读写和运行代码仍隔离。
具体内部路径和运行/交接命令见[隔离操作说明](ISOLATION.md)，不要求用户操作这些路径。
每个窗口都应知道另两个窗口也在工作，不清理或回滚他人改动，不执行全目录格式化或批量暂存。

| 窗口 | 独占写入范围（相对各自worktree的qrefactorbench） |
|---|---|
| A | `pilot/parallel-20260929/cases/` |
| B | `pilot/parallel-20260929/implementation/`及明确负责的项目模块；在自己的worktree维护集成状态 |
| C | `pilot/parallel-20260929/evaluation/`；论文只使用原FSE的`paper/`，沿用用户的Overleaf Git流程 |

原FSE的研究源码和其他窗口源码只读；论文是单独管理的唯一原`paper/`目录，不创建论文worktree或阅读副本。
需修改runner、schema或评测器时，先将具体补丁方案交B安排单一负责人，
在其自己的worktree实现；其他窗口接收固定版本，不直接import该开发目录。本轮优先复用现有实现。
所有窗口完成本地README、验证和交接；B收到产物后再更新自己的集成状态，其他窗口不重复更新总状态。
C负责论文内容，A给文献素材、B给design事实；结果表保持空白，未实现方法标提案。
论文仍按用户既有Overleaf Git流程管理，不自动pull/push、建分支或新仓库；编辑前核对原paper的未提交内容。
B的集成结果回写原FSE前先核对原目录新改动，不自动覆盖、提交、合并或推送。
这调整任务与文档写入职责，既有科学审批规则不变；正式case/gold/split/指标不随分工改变。

## 固定版本的交接

每份可交接包至少含：本地README（状态、结论、下一步）、输入清单及SHA256、验证命令与实际结果、
限制、交接说明。目录使用明确版本；已交接输入不原地改写，修正另建版本。未创建的产物不写成已完成。
接收窗口自行核对文件与哈希，记录接受的具体版本；引用对方正在修改的“最新目录”不能启动实验。
交付使用`parallel_snapshot.py`生成独立只读快照，再复制到接收者自己的imports并核验。
实验运行前另冻结本窗口的完整qrefactorbench代码，使用`parallel_run.sh --snapshot`启动，
数据/私有参考也固定版本。具体命令及环境/资源锁规则见[隔离操作说明](ISOLATION.md)。

最小交接字段：`artifact_id`、`producer`、`status`、`input_paths_and_sha256`、`output_paths`、
`validation_commands_and_results`、`limitations`、`next_consumer`。JSON或Markdown均可，不新增通用框架。

- A → B/C：来源、经典程序、行为判据、覆盖/前沿证据、公开输入与私有参考的分界及纳入状态。
- B → C：已测试实现、接口、design事实和开发失败证据；不给方法开发者最终隐藏测试答案。
- C → B：评测协议、对照/消融、预算/统计单位、所需日志；B统一执行实验后返回实际记录。
- A不根据模型输赢筛选最终题目；C不把方案/空表写成已实现或已实测，设计与实现有差异时明确保留。

## 运行与证据边界

仅B派发本轮模型实验，避免重复采样和三个窗口抢同一额度。D-035的同方向现有订阅授权仍有效：
先固定具体协议、输入、预算上限和隔离验收；满足授权范围后直接执行，无需再次申请调用次数。
新候选未纳入、新家族未确定或协议证据不足时，先完成独立准备，不能用本说明补足科学授权。
历史终止队列不重启、不追加采样。新付费渠道、QPU、依赖安装及外部发布仍按原边界处理。

A/C默认做资料、有限经典检查、协议和写作，B负责实现和集成。大规模模拟和长时资源任务由B协调运行窗口；
不共享可写缓存/输出，不同时占满主机。研究窗口可以读项目上下文，被测模型只接收协议允许的公开输入。
开发/最终评测按独立母程序或来源谱系隔离；同一程序不同输入不是独立母案例。
只通过输入输出检查、纯经典回退、实际量子计算和完整收益分别记录。

## 启动方式

三个对话都从用户熟悉的原FSE开始。用户不需要记ABC、三个任务或任何路径，
也不需要固定口令；说“现在怎么推进”或“想开几个窗口一起做”只是自然语言示例。
Agent读取PROJECT_STATUS、NEXT_ACTIONS和本说明，根据当前进度说明适合并行的任务。
上面的三条线是当前安排，不是要求用户记忆的永久菜单；后续调整由Agent维护文档。

新对话只说“继续”即可：尚未确定负责范围时，Agent主动列出当前任务的编号选项，
每项一句话并标推荐项；用户选编号或说“就推荐的”即可，不要求用户先报任务名或先询问分工。
用户若已主动指定任务则直接对应：文献/案例对应内部A，代码开发对应B，实验设计/论文对应C。
确定任务后，Agent读取相应WINDOW.md及当地AGENTS.md，后续每次命令指定该worktree工作目录，
编辑使用其绝对路径。同一对话里的“继续”继承该任务，不要求用户重复指定。
原FSE入口及本说明优先于旧副本要求用户切换目录的启动文字；其他隔离和科学边界仍有效。

不需要第四个协调窗口，也不自动创建子Agent。未确定任务时先恢复进度并说明分工，
不能把任意新对话的“继续”解释为已自动认领某个空闲窗口；当前没有自动认领服务。
没有已确定任务的新对话先展示选项，不直接占用总NEXT_ACTIONS中的任务。仅询问方案不会启动研究实验。
