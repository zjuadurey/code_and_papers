# v0.1.1：修复无依据的设备数量限制，并实际测量

2026-09-21。用户指出原程序允许 16 个设备，而原型人为限制 6 个，要求采取行动。
本次修复只恢复设备数量范围，并做本地执行检查；不修改 benchmark 合同或科学标签。

## 改了什么

- 当前 [protocol.json](../../protocol.json) 从 v0.1.0 升至 v0.1.1，`max_qubits` 由 6 改为 16。
- [solve](../../hybrid_program.py) 的越界错误改为原接口的 `ValueError`；公共入口仍先用
  原 `prepare_request` 校验，17 个设备在进入求解器前拒绝。
- QAOA 层数、初始参数、优化器、80 次评估预算、256 shots、seed=7 和样本选解规则未变。
- 没有添加经典精确解兜底或根据失败答案调参重跑。
- 原实现/协议/测试/说明已逐字保存在 [original_source](original_source/)，
  [manifest](original_source_manifest.json) 可核对原首次运行记录中的源码 hash。
  原 first_run.json、日志、validation.json 均保留原样；其中的路径/hash 描述历史版本，
  现在应与该快照对应，不能要求修改后的工作文件仍具有原 hash。

**仅修复设备数量范围。** 既有 `max_total_weight=2**40` 限制仍在；它不属于原程序
的任意精度整数合同。这一精度/输入域问题没有被本次设备上限修复解决。
有限采样的全局最优与指定并列结果也没有得到保证。

## 真正执行的结果

固定四个检查输入：7/12/16 设备的加权路径图，以及 16 设备的加权完全图。
生成规则和完整输入在执行前写入 [manifest](runs/manifest.json)；输入用于工程边界检查，
不是新增 benchmark cases、随机代表性样本或科学成功率估计。

| 输入 | 需求边数 | 混合调用耗时 | 进程峰值内存 | 返回冲突成本 / 原最优成本 | 完整报告一致 |
|---|---:|---:|---:|---:|---|
| [path_7](runs/path_7.json) | 6 | 0.155 s | 127.91 MiB | 0 / 0 | 是 |
| [path_12](runs/path_12.json) | 11 | 0.284 s | 141.67 MiB | 0 / 0 | 是 |
| [path_16](runs/path_16.json) | 15 | 2.915 s | 384.73 MiB | 4 / 0 | 否 |
| [dense_16](runs/dense_16.json) | 120 | 8.888 s | 385.34 MiB | 141 / 136 | 否 |

四次均实际运行 Qiskit、正常返回，首次尝试保留，无重试。四次优化器都达到 80 次
评估预算并报告未收敛。参考程序在混合结果保存之后才运行，不给优化器反馈。
两个 16 设备结果确实不是最优解；这不是只缺少证明，也不是单纯并列顺序差异。
不得把表中的“执行成功”当成完整迁移成功。

计时只包含混合函数调用，不含模块导入和随后经典参考核对。内存使用 Linux
`ru_maxrss`，在混合返回后、参考运行前读取，单位 KiB 转 MiB；是含解释器、Qiskit、
临时数组和诊断输出的进程峰值，不是纯状态向量大小，也不是相对基线净增量。
每例新进程；OMP/OPENBLAS/MKL 线程设置为 1（与原运行未固定线程的环境不同，已记录），
单例超时预算 300 秒，无超时。优化使用理想 Statevector 精确期望，未执行硬件作业。
这些单次本地测量只回答“能否运行、需要多少本地资源”，不用于量子加速或性能排名。
